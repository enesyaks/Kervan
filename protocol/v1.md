# Kervan protocol v1

Mac app ↔ server. Server code: `server/src/protocol.ts`. Mac code: `mac/Sources/KervanKit/Protocol.swift`.
Both must change together; bump `PROTOCOL_VERSION` on any breaking change.

## Transport

- WebSocket at `ws://<host>:7420/v1/ws` (Tailscale only, so no TLS at this layer).
- Auth: `Authorization: Bearer <token>` header on the upgrade request.
  Wrong or missing token → HTTP `401` before the upgrade, no socket is opened.
- One JSON object per text frame. Every message has a `type`.
  Requests that expect a reply carry an `id` (client-chosen string); the reply echoes it.
- Server sends WebSocket ping frames every 30 s and drops clients that don't pong.

## Handshake

The client's first message must be `hello`. Until then the server answers everything else with
`error` / `hello_required`.

```json
→ {"type":"hello","protocol":1,"client":{"name":"Kervan for Mac","version":"0.1.0"}}
← {"type":"welcome","protocol":1,"server":{"name":"kervan","version":"0.1.0"},"agents":["claude","codex"],
   "agentDetails":[{"id":"claude","name":"Claude Code"},{"id":"codex","name":"Codex"}]}
```

After `welcome` the client receives every `session.updated` and `session.event` broadcast, for all sessions.

If `protocol` is not supported the server replies `error` / `unsupported_protocol` and closes with code `4000`.

## Messages

### Client → server

| type              | fields                                        | reply |
|-------------------|-----------------------------------------------|-------|
| `hello`           | `protocol: number`, `client: {name, version}` | `welcome` |
| `ping`            | `id`                                          | `pong` |
| `session.create`  | `id`, `agent`, `skills?: string[]`, `mcpServers?: string[]`, `orchestrate?: boolean` | `session.created` (status `starting`) |
| `mcp.list`        | `id`                                          | `mcp.list.result` |
| `mcp.save`        | `id`, `server: {name, transport: stdio\|http, command?, args?, env?, url?, headers?}`; a `null` env/header value keeps the stored one | `mcp.list.result` |
| `mcp.delete`      | `id`, `name`                                  | `mcp.list.result` |
| `agent.list`      | `id`                                          | `agent.list.result` |
| `agent.save`      | `id`, `agent: {id, name, command (path, PATH name or `builtin`), args?, authMethod?, skillsDir?, env?, node}`; the server starts it once before keeping it; `null` env keeps the stored value | `agent.list.result`, then `agents.updated` to everyone |
| `agent.delete`    | `id`, `agentId` (only agents added from the app) | `agent.list.result`, then `agents.updated` |
| `session.list`    | `id`                                          | `session.list.result` |
| `session.history` | `id`, `sessionId`                             | `session.history.result` |
| `session.prompt`  | `id`, `sessionId`, `text` (1–100 000 chars), `attachments?: string[]` (≤ 20 workspace paths) | `ok`, then events |
| `session.cancel`  | `id`, `sessionId`                             | `ok`; open permission requests resolve as `cancelled` |
| `session.permission` | `id`, `sessionId`, `requestId`, `optionId` (one of the request's options) | `ok` |
| `session.rename`  | `id`, `sessionId`, `title` (1–120 chars)      | `ok`, then `session.updated` |
| `session.archive` | `id`, `sessionId`, `archived: boolean`        | `ok`, then `session.updated` |
| `session.search`  | `id`, `query`                                 | `session.search.result` |

### Server → client

| type                     | fields                                                      |
|--------------------------|-------------------------------------------------------------|
| `welcome`                | `protocol`, `server: {name, version}`, `agents: string[]` (ids, default first), `agentDetails: [{id, name}]` |
| `pong` / `ok`            | `id`                                                        |
| `error`                  | `code`, `message`, `id?` (the failed request's id, also for malformed requests that carry one) |
| `session.created`        | `id`, `session: SessionInfo`                                |
| `session.list.result`    | `id`, `sessions: SessionInfo[]`                             |
| `session.history.result` | `id`, `sessionId`, `events: SessionEvent[]`                 |
| `session.updated`        | `session: SessionInfo` (broadcast)                          |
| `session.event`          | `sessionId`, `event: SessionEvent` (broadcast)              |
| `agent.list.result`      | `id`, `agents: [{id, name, command, args, authMethod?, skillsDir?, envKeys, node, source: builtin\|app, available}]`, `nodes` |
| `agents.updated`         | `agents`, `agentDetails` (broadcast; same shape as in `welcome`) |
| `mcp.list.result`        | `id`, `servers: [{name, transport, command?, args?, url?, envKeys, headerKeys}]` — secret values are never sent |
| `session.search.result`  | `id`, `hits: [{sessionId, seq, role: user\|agent, snippet}]` (best first, ≤ 50) |

`SessionInfo`: `{id, agent, title, status, createdAt, archived, skills, mcpServers, error?}`; `status` is `starting | idle | running | waiting | error | closed`; `waiting` means a permission request is open.
Only `idle` sessions accept a prompt.

`SessionEvent`: `{seq, at, kind, ...}` — `seq` starts at 1 per session and has no gaps.

| kind                       | fields                                         |
|----------------------------|------------------------------------------------|
| `user_message`             | `text`, `attachments?`                          |
| `agent_message_chunk`      | `text` (append to the current agent message)   |
| `agent_thought_chunk`      | `text`                                         |
| `tool_call`                | `toolCallId`, `title`, `toolKind`, `status`    |
| `tool_call_update`         | `toolCallId`, `title?`, `status?`              |
| `permission_request`       | `requestId`, `title`, `toolKind`, `detail?`, `options: [{optionId, name, kind}]` |
| `permission_resolved`      | `requestId`, `outcome: selected \| cancelled`, `optionId?` |
| `turn_end`                 | `stopReason` (ACP reasons, plus `interrupted` when a server restart cut the turn off) |
| `notice`                   | `text` — something Kervan did, e.g. resuming the agent |
| `error`                    | `message`                                      |

Clients must ignore event kinds they don't know.

### Error codes

| code                   | meaning                                  |
|------------------------|------------------------------------------|
| `bad_message`          | frame is not a JSON object with a string `type`, or fields are missing |
| `unknown_type`         | `type` is not defined in this version    |
| `hello_required`       | a message arrived before `hello`         |
| `unsupported_protocol` | `hello.protocol` is not supported        |
| `unknown_agent`        | `session.create` named an agent the server doesn't have |
| `unknown_session`      | no session with that id                  |
| `session_busy`         | the agent is still answering the previous prompt |
| `session_unavailable`  | the session is starting, errored or closed |
| `unknown_request`      | no open permission request with that id  |

Clients must ignore server message types they don't know, so the server can add types without a version bump.

A `permission_request` without a later `permission_resolved` for the same `requestId` is still open:
the agent waits, however long the user is away. `kind` of an option is `allow_once | allow_always | reject_once | reject_always`.

## Persistence

Sessions and events are stored in SQLite (`$KERVAN_DATA_DIR/kervan.db`). After a server restart every session
is listed again with its full history; an interrupted turn ends with `turn_end`/`interrupted`, open permission
requests resolve as `cancelled`, and the next prompt resumes the same agent conversation (ACP `session/resume`).

## Files (HTTP)

Same host and port, same `Authorization: Bearer <token>` header. Paths are workspace-relative, `/`-separated,
each segment URL-encoded. Absolute paths, `..` and symlinks leading out of the workspace are refused with `400`.

| request | result |
|---|---|
| `GET /v1/sessions/:id/files` | `200 {entries: [{path, type: file\|dir, size, modifiedAt}], truncated}` — skips `.git`, `node_modules`; at most 5000 entries |
| `GET /v1/sessions/:id/files/<path>` | `200` file bytes (`application/octet-stream`) |
| `PUT /v1/sessions/:id/files/<path>` | `201 {path, size}`; body is the raw file; parents are created; `413` above `KERVAN_MAX_UPLOAD_MB` (default 512) |

Errors: `401` bad token, `404` unknown session or file, `400` bad path. Attachments in `session.prompt` reach the
agent as ACP `resource_link` blocks with `file://` URIs; uploading first and then attaching is the client's job.

## Search

Whole messages are indexed (an agent's streamed chunks are joined). Every query word must match, as a word prefix.
Matching ignores case and Turkish/Latin diacritics, and treats `ı`, `İ`, `I` as `i`, so `rotasi` finds `rotası`.
`seq` is the first event of the matched message — the same id the client uses for that transcript row. In `snippet`
(≈120 chars of the original text) each match is wrapped in `\u0001` … `\u0002`.

## Skills (HTTP)

| request | result |
|---|---|
| `GET /v1/skills` | `200 {skills: [{name, description, files}]}` — only skills whose `SKILL.md` exists |
| `PUT /v1/skills/<name>/<path>` | `201`; upload one file of the skill (name: lowercase, digits, `-`) |
| `DELETE /v1/skills/<name>` | `204` |

Skills chosen at `session.create` are copied into the workspace (the agent's own skills folder, e.g.
`.claude/skills`, else `.kervan/skills`), and the agent's first prompt carries a hidden note listing them.
MCP servers chosen there are passed to the agent with ACP `session/new` and `session/resume`; HTTP servers are
skipped (with a `notice`) for agents that don't support them.

## Roles and teams (M8)

| request | reply |
|---|---|
| `role.list` `{id}` | `role.list.result {id, roles: [{id, name, agent, instructions, skills, mcpServers}]}` |
| `role.save` `{id, role}` | `role.list.result`; agent, skills and MCP servers must exist |
| `role.delete` `{id, roleId}` | `role.list.result` |
| `team.create` `{id, title, roles: string[]}` (1–8) | `team.created {id, team: {id, title, createdAt, sessionIds}}`, then `team.updated` to everyone |
| `team.list` `{id}` | `team.list.result {id, teams}` |

A team starts one session per role, all in one shared folder (`workspaces/team-<id>`). Member sessions carry
`teamId` and `role` (the role's name, also their initial title). The role's instructions reach the agent in the
hidden note before its first message.

## Lead agents and helpers (M9)

A session created with `orchestrate: true` (or a team member whose role has `lead: true`) is a **lead**. Its agent
gets an extra stdio MCP server named `kervan` (`server/src/orchestra-mcp.ts`) with these tools:
`list_agents`, `start_helper {name, task, agent? | role?}`, `message_helper {helperId, text}`,
`wait_for_helper {helperId, timeoutSec?}` (default 50 s, max 600; returns `done: false` on timeout),
`list_helpers`, `stop_helper {helperId}`. At most 6 helpers per lead; helpers can't start helpers.

The bridge talks to the server over a Unix socket (`<dataDir>/orchestra.sock`, owner-only) with a per-start token
that names the lead, so a lead only reaches its own helpers. The MCP name `kervan` is reserved.

Helpers are ordinary sessions with `parentId` set to the lead; they work in the lead's folder (and join its team).
Messages the lead sends them are `user_message` events with `from: <lead session id>`. Their permission requests
reach the app like any other session's. A lead's own calls to these tools are approved by Kervan without a card
(matched by exact tool title; shell commands and edits always ask).

## Budgets, limits and helper worktrees (M11)

- `session.create` takes `budgetUsd` (0–10000) with `orchestrate: true`; roles with `lead: true` may carry `budgetUsd`.
  `SessionInfo.usage {contextUsed, contextSize, costUsd?}` is what the agent last reported (ACP `usage_update`;
  cost only from agents that report one, cumulative across restarts). When a lead's and its helpers' cost reaches
  the budget, Kervan records a notice on the lead, cancels every running turn in the crew, and refuses
  `start_helper` / `message_helper`.
- Server limits: `KERVAN_MAX_HELPERS` (default 6 per lead), `KERVAN_HELPER_TURN_MINUTES` (default 30; 0 = off).
  A helper turn past the limit is cancelled with a notice.
- If the lead's folder is a git repository with a commit, `start_helper` (unless `isolate: false`) gives the helper
  its own worktree (`<workspaces>/worktree-<id>`) on branch `kervan/<name>-<id8>` (`SessionInfo.branch`).
  `helper_diff` shows the branch's changes (uncommitted work is committed first); `merge_helper` merges it into the
  lead's current branch with `--no-ff`, or aborts and lists the conflicting files. `merge_helper` is the one Kervan
  tool that is not auto-approved.

## Agent settings, terminal agents and resilience (M12)

- `SessionInfo.config: [{id, name, category?, value, choices: [{value, name, description?}]}]` holds the agent's
  select-style ACP session config options (model, thought_level, mode…), from `session/new`, `session/resume` and
  `config_option_update`. `session.config {id, sessionId, configId, value}` changes one (`session/set_config_option`);
  without a running agent the choice is stored, and it is re-applied whenever the agent restarts. Agents that offer
  models and modes the older way (Gemini CLI: `models` / `modes` on session/new and session/resume) get them as
  options `acp:model` and `acp:mode`, changed with `session/set_model` / `session/set_mode`.
- Agents with `protocol: pty` (agents.yaml or the app) run in a pseudo-terminal via `python3`'s `pty` module: each
  message is typed as one line, output (control sequences stripped, echo removed) streams back as
  `agent_message_chunk`, and a turn ends after `quietMs` (default 2000) of silence. No resume, preface or permission
  requests; they can't be leads. `agentDetails[].terminal` marks them.
- An agent process that exits on its own no longer ends the session: a notice is recorded and the next message
  starts it again (resumed, for ACP agents).
- The server copies its database to `<dataDir>/backups/kervan-YYYY-MM-DD.db` once a day (`VACUUM INTO`), keeping 7.

## Nodes (M13)

With `KERVAN_NODE_TOKEN` set, the hub accepts `kervan-node` processes on `/v1/node` (bearer = node token, header
`x-kervan-node: <name>`). Hub and node then make JSON calls both ways (`rpc.ts`): the hub calls `start`, `prompt`,
`cancel`, `close`, `setConfig`, `files.list|read|write` (base64, ≤ 50 MB); the node sends `event`, `usage`,
`config`, `exited` and calls `permission`. Workspaces on a node are keys (session or `team-<id>`) relative to its
own folder. App-side: agents carry `node` (agent.save, `agentDetails[].node`), `agent.list.result.nodes` lists the
assignable nodes, `node.list` → `node.list.result {nodes: [{name, connected, version?, lastSeen?}]}`, and
`nodes.updated` is broadcast on connect/disconnect. Messages to a session whose node is offline fail with
`node_offline` and leave the session as it is; file routes answer 503.
