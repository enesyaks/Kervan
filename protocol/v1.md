# Kervan protocol v1

Mac app ↔ server. Server code: `server/src/protocol.ts`. Mac code: `mac/Sources/KervanKit/Protocol.swift`.
Both must change together; bump `PROTOCOL_VERSION` on any breaking change.

## Transport

- WebSocket at `ws://<host>:7420/v1/ws` (Tailscale or private LAN, so no TLS at this layer).
- Auth: `Authorization: Bearer <token>` header on the upgrade request.
  Wrong or missing token → HTTP `401` before the upgrade, no socket is opened.
- The web client (served at `/` while web access is on) never uses the server's token. A browser is paired first:
  `POST /v1/web/pair` with `{"code": "ABCD-EFGH", "name": "iPhone · Safari"}` trades a one-time code from
  `web.pair` (valid 10 minutes) for `{"token", "device"}`; wrong or used codes get `401`, web access off `403`.
  Browsers can't set headers on a WebSocket, so the device token goes in subprotocols instead: `kervan` and
  `kervan.key.<device token, base64url-encoded>`. The server answers with `kervan` only, so the key is never echoed.
  `GET /v1/check` with a Bearer token answers `200` or `401`.
- A paired browser may send only `ping`, `project.list`, `project.map.get`, `board.list` and `session.list`, `history`, `create`, `prompt`, `cancel`, `permission`,
  `rename`, `autoApprove`, `archive`, `search`, `config`, and `session.changes` to read a session's changes (undoing, committing and pull requests stay
  with the app); anything else gets `error` / `forbidden`, before the request's fields are checked. Unasked it hears only
  `session.updated`, `session.event`, `agents.updated`, `projects.updated` and `board.updated`. Tool events reach it without
  `diffs`, and `session.changes` without the diffs of files that look like secrets (`.env`, keys, credentials), listed in `hiddenPaths`. When the device is revoked or web
  access is turned off, its sockets close with code `4001`.
- Ten failed browser sign-ins (pairing codes, check, device keys) from one address within ten minutes get `429` until
  the window passes. The app's own Bearer connection is never limited.
- One JSON object per text frame. Every message has a `type`.
  Requests that expect a reply carry an `id` (client-chosen string); the reply echoes it.
- Server sends WebSocket ping frames every 30 s and drops clients that don't pong.
- Maximum WebSocket frame payload is 1 MB (`1024 * 1024` bytes). Binary frames on `/v1/ws` are rejected with `bad_message`.

## Handshake

The client's first message must be `hello`. Until then the server answers everything else with
`error` / `hello_required`.

```json
→ {"type":"hello","protocol":1,"client":{"name":"Kervan for Mac","version":"0.1.0"}}
← {"type":"welcome","protocol":1,"server":{"name":"kervan","version":"0.2.0"},"agents":["claude","codex"],"agentDetails":[{"id":"claude","name":"Claude Code"},{"id":"codex","name":"Codex"}]}
```

After `welcome` the client receives every broadcast: `session.updated` and `session.event` (for all sessions),
`agents.updated`, `nodes.updated`, `projects.updated`, `schedules.updated`, and `team.updated`.

If `protocol` is not supported the server replies `error` / `unsupported_protocol` and closes with code `4000`.

### Core structures

`SessionInfo`:
```typescript
{
  id: string;
  agent: string;
  title: string;
  status: "starting" | "idle" | "running" | "waiting" | "error" | "closed";
  createdAt: string;
  archived: boolean;
  skills: string[];
  mcpServers: string[];
  teamId?: string;
  role?: string;
  parentId?: string;
  orchestrate?: boolean;
  budgetUsd?: number;
  branch?: string;
  usage?: { contextUsed: number; contextSize: number; costUsd?: number };
  config?: ConfigOption[];
  projectId?: string;
  scheduleId?: string;
  autoApprove?: boolean;
  error?: string;
}
```
Only `idle` sessions accept a prompt. `waiting` means a permission request is open.

`SessionEvent`: `{ seq: number, at: string, kind: string, ... }` — `seq` starts at 1 per session and has no gaps.

| kind | fields |
|---|---|
| `user_message` | `text`, `attachments?: string[]`, `from?: string` (lead session id when written by a lead agent) |
| `agent_message_chunk` | `text` (append to current agent message) |
| `agent_thought_chunk` | `text` |
| `tool_call` | `toolCallId`, `title`, `toolKind`, `status`, `diffs?: FileDiff[]` |
| `tool_call_update` | `toolCallId`, `title?`, `status?`, `diffs?: FileDiff[]` |
| `plan` | `entries: [{content, status, priority}]` — replaces the whole plan |
| `commands` | `commands: [{name, description, hint?}]` — replaces the slash command list |
| `checkpoint` | `commit: string`, `messageSeq: number` — folder snapshot taken before user message `messageSeq` |
| `permission_request` | `requestId`, `title`, `toolKind`, `detail?`, `options: [{optionId, name, kind}]` |
| `permission_resolved` | `requestId`, `outcome: "selected" \| "cancelled"`, `optionId?` |
| `turn_end` | `stopReason: string` (ACP stop reason, or `"interrupted"` on server restart) |
| `notice` | `text: string` — action Kervan took (recovering session, reverting files, git commit) |
| `error` | `message: string` |

Clients must ignore event kinds and server message types they don't know.

### Error codes

| code | meaning |
|---|---|
| `bad_message` | frame is not JSON, missing required fields, field value exceeds limits, or operation not supported for this session/target |
| `unknown_type` | `type` is not defined in this version |
| `hello_required` | a message arrived before `hello` |
| `unsupported_protocol` | `hello.protocol` is not supported (server closes socket with code 4000) |
| `unknown_agent` | `session.create` or `schedule.save` named an agent the server doesn't have |
| `unknown_session` | no session with that id |
| `session_busy` | the agent is still answering the previous prompt, or running/waiting during a revert |
| `session_unavailable` | the session is starting, errored or closed |
| `unknown_request` | no open permission request with that id |
| `node_offline` | the node assigned to run this session is not connected right now |

A `permission_request` without a later `permission_resolved` for the same `requestId` is open:
the agent waits until the user answers. `kind` of an option is `allow_once | allow_always | reject_once | reject_always`.

## Persistence

Sessions and events are stored in SQLite (`$KERVAN_DATA_DIR/kervan.db`). After a server restart every session
is listed again with its full history; an interrupted turn ends with `turn_end`/`interrupted`, open permission
requests resolve as `cancelled`, and the next prompt resumes the same agent conversation (ACP `session/resume`).

## Files (HTTP)

Same host and port, same `Authorization: Bearer <token>` header. Paths are workspace-relative, `/`-separated,
each segment URL-encoded. Absolute paths, `..` and symlinks leading out of the workspace are refused with `400`.

| request | result |
|---|---|
| `GET /v1/sessions/:id/files` | `200 {entries: [{path, type: "file"\|"dir", size, modifiedAt}], truncated: boolean}` — skips `.git`, `node_modules`, and temporary uploads; sorted by path; at most 5000 entries |
| `GET /v1/sessions/:id/files/<path>` | `200` file bytes (`application/octet-stream`), with `Content-Disposition: attachment; filename*=UTF-8''...` |
| `PUT /v1/sessions/:id/files/<path>` | `201 {path, size}`; body is the raw file; parents are created; streamed to a temporary file then atomic rename; `413` above `KERVAN_MAX_UPLOAD_MB` (default 512 MB) |
| `POST /v1/sessions/:id/files?name=<file>` | `201 {path, size}` with `path` = `uploads/<file>`; the name may also come as an `x-file-name` header or `Content-Disposition` (`filename*=UTF-8''…`). A bare file name only: `/`, `\`, `.` and `..` are refused with `400`, and so is a badly %-encoded one |

| `PUT /v1/cards/files?name=<file>` | `201 {file, size}`: a file for a board card, kept on the server until the card starts. `file` is `<upload id>/<file>`; put it in the card's `files`. The app's key only; the same name rules and `413` limit |

A paired browser (web access) may only add files this way, into `uploads/`; any other file request with a device key
gets `403`. The app's own key is never rate-limited.

Errors: `401` bad token, `404` unknown session or file not found, `400` bad path, `413` too large, `503` node offline (for sessions on a remote node).
For sessions on a remote node, files are transferred over the node RPC connection (individual file size capped at `MAX_NODE_FILE_BYTES` = 50 MB).

Attachments in `session.prompt` reach the agent as ACP `resource_link` blocks with `file://` URIs; uploading first and then attaching is the client's job.

## Checkpoints, file changes and rewinding

Before every user prompt, Kervan automatically snapshots the session's workspace in a private git store
under `$KERVAN_DATA_DIR/checkpoints/<sessionId>` (excluding `node_modules`, `venv`, `build`, etc.). The workspace's
own `.git` directory is never modified by checkpoint snapshots. A `checkpoint` event is recorded with the commit hash
and `messageSeq`.

### `session.changes`
Returns files changed since the session's first message (`since: "session"`, the default) or since the last message (`since: "turn"`).
Changes are computed using git diff against the checkpoint. `patch` is truncated to 400 000 characters if too large.
Fails with `bad_message` for sessions located on a remote node ("changes can only be followed for agents on this server, not on a node").

```json
→ {"type":"session.changes","id":"c-1","sessionId":"sess-1","since":"session"}
← {"type":"session.changes.result","id":"c-1","sessionId":"sess-1","changes":{"files":[{"path":"src/index.ts","status":"modified","additions":4,"deletions":1}],"patch":"diff --git a/src/index.ts b/src/index.ts\n--- a/src/index.ts\n+++ b/src/index.ts\n@@ -1,3 +1,6 @@\n...","truncated":false,"sinceSeq":1,"repository":true,"branch":"main"}}
```

### `session.revert`
Reverts files in the workspace to their state before the user message `seq`. If `paths` is omitted, all modified
files are rewound and newly created files are removed. If `paths` is specified (1–500 workspace paths), only those files are reverted.
The session must be `idle` (fails with `session_busy` if the agent is running). A `notice` event is recorded, and Kervan
injects a hidden note into the session so the agent is informed of the rewind on its next turn.

```json
→ {"type":"session.revert","id":"r-1","sessionId":"sess-1","seq":1,"paths":["src/index.ts"]}
← {"type":"ok","id":"r-1"}
```

### `session.commit`
Commits all uncommitted changes in the session folder into its own git repository using git commit (`1–5000` chars message).
The folder must be a git repository. Records a `notice` event with the short commit hash and subject.
Fails with `bad_message` if the folder is not a git repository or there is nothing to commit.

```json
→ {"type":"session.commit","id":"m-1","sessionId":"sess-1","message":"Implement user authentication"}
← {"type":"ok","id":"m-1"}
```

### `session.pullRequest`
Puts the session's work up for review. The folder must be a git repository with an `origin` remote.

1. If the folder is on the remote's default branch (`base`), a branch `kervan/<title>-<session id>` is created
   there, so the base branch is left as it was.
2. Whatever is uncommitted is committed with `title` as the message.
3. The branch is pushed to `origin` (`git push -u`), without ever waiting for a password.
4. If the server has the GitHub CLI signed in, `gh pr create` opens the pull request: `created: true`, `url` is the
   pull request. Otherwise `created: false`, and `url` is GitHub's compare page for the branch (missing for other hosts).

Records a `notice` event. Fails with `bad_message` when the folder isn't a repository, has no `origin`, has nothing
the base branch lacks, or the push is refused (the message says how to give the server push access).

```json
→ {"type":"session.pullRequest","id":"pr-1","sessionId":"sess-1","title":"Fix the login redirect","body":"Closes #12"}
← {"type":"session.pullRequest.result","id":"pr-1","sessionId":"sess-1","pullRequest":{"branch":"kervan/fix-the-login-redirect-sess-1","base":"main","url":"https://github.com/acme/app/pull/34","created":true}}
```

## Projects

A project connects sessions to a shared directory on the server with instructions given to every agent before its
first prompt. Projects are stored in `$KERVAN_DATA_DIR/projects.json`.

`ProjectInfo`:
```typescript
{
  id: string;
  name: string;        // 1–80 characters
  path: string;        // absolute path on the server
  instructions: string;// up to 20 000 characters
  createdAt: string;   // ISO timestamp
  map?: {              // the project map, once one was asked for
    status: "building" | "ready" | "failed";
    agent: string;     // the agent that builds or built it
    commit?: string;   // HEAD of the project folder when the map was started; absent outside git
    updatedAt: string; // ISO timestamp
    sessionId?: string;// the mapping session
    error?: string;    // why the last try failed
  };
}
```

- `project.list`: Returns all projects sorted alphabetically by name.
- `project.save`: Takes `{ id?, name, instructions?, path?, gitUrl?, mapAgent? }`.
  - `mapAgent` (new projects only): an agent that maps the project right after it's made, as `project.map` does. An unknown agent refuses the save.
  - To create a new project: specify `path` (must be an existing directory on the server), or `gitUrl` (`https://`, `ssh://`, or `git@` URL cloned into `$KERVAN_WORKSPACES_DIR/projects/<slug>`), or neither (creates an empty directory in workspaces).
  - To edit an existing project: specify `id`; only `name` and `instructions` can be changed.
  - Broadcasts `projects.updated` to all connected clients.
- `project.delete`: Removes the project registration by `projectId` (the folder on disk and existing sessions are kept). Broadcasts `projects.updated`.
- `project.map`: Starts (re)building the project map with `agent`, which must run on this server. A session titled "Project map"
  works in the project folder itself (not a worktree) and is asked to read the repository and answer with a Markdown map
  of it: what it does, commands, layout, entry points, where each kind of work lives, conventions. Its answer (cut to
  40 000 characters) is kept in `$KERVAN_DATA_DIR/project-maps/<projectId>.md`, never in the repository, and the session
  is archived. `map.status` goes `building` → `ready` or `failed`; a map still building when the server restarts is
  `failed`. Refused while a map is already building. Every later session in the project gets the last map that was
  built, with its commit, in the text before its first prompt, and is told to go to the files its task is about rather
  than rescan the repository, and to check `git log --stat <commit>..HEAD` for what changed since.
- `project.map.get`: The last map that was built (also while a new one builds or after one failed).

```json
→ {"type":"project.list","id":"p-1"}
← {"type":"project.list.result","id":"p-1","projects":[{"id":"proj-101","name":"Web App","path":"/srv/kervan/workspaces/projects/web-app","instructions":"Follow TypeScript strict mode.","createdAt":"2026-03-01T12:00:00.000Z"}]}

→ {"type":"project.save","id":"p-2","project":{"name":"API Service","instructions":"Use Node 24 and fastify","gitUrl":"https://github.com/example/api.git"}}
← {"type":"project.list.result","id":"p-2","projects":[...]}
← {"type":"projects.updated","projects":[...]}

→ {"type":"project.delete","id":"p-3","projectId":"proj-101"}
← {"type":"project.list.result","id":"p-3","projects":[...]}
← {"type":"projects.updated","projects":[...]}
```

When creating a session with `session.create`, providing `projectId` assigns the session to that project's directory and
prepends the project's instructions to the agent's preface.

## Scheduled tasks

Tasks run automatically on the server on a schedule, starting a new session and sending it an initial prompt.
Tasks are stored in `$KERVAN_DATA_DIR/schedules.json` and evaluated every 30 seconds.

`ScheduleWhen`:
- `{ kind: "daily", time: "HH:MM", weekdays: number[] }` — `weekdays` are 1 (Monday) through 7 (Sunday).
- `{ kind: "interval", minutes: number }` — repeat interval from 5 minutes to 7 days (`10 080` minutes).

`ScheduleInfo`:
```typescript
{
  id: string;
  title: string;       // 1–80 characters
  agent: string;       // must exist in catalog
  projectId?: string;  // optional project id
  prompt: string;      // 1–20 000 characters
  when: ScheduleWhen;
  timeZone: string;    // valid IANA time zone (e.g. "Europe/Istanbul")
  enabled: boolean;
  createdAt: string;
  lastRunAt?: string;
  lastSessionId?: string;
  lastError?: string;
}
```

- `schedule.list`: Returns all scheduled tasks sorted by title.
- `schedule.save`: Creates or updates a schedule. Broadcasts `schedules.updated` to all clients.
- `schedule.delete`: Deletes a schedule by `scheduleId`. Broadcasts `schedules.updated`.
- `schedule.run`: Manually triggers the task immediately. Resolves after starting the session, and broadcasts `schedules.updated`.

```json
→ {"type":"schedule.list","id":"s-1"}
← {"type":"schedule.list.result","id":"s-1","schedules":[{"id":"sch-1","title":"Morning audit","agent":"claude","prompt":"Run tests and review open issues","when":{"kind":"daily","time":"09:00","weekdays":[1,2,3,4,5]},"timeZone":"Europe/Istanbul","enabled":true,"createdAt":"2026-03-01T08:00:00.000Z"}]}

→ {"type":"schedule.save","id":"s-2","schedule":{"title":"Hourly health","agent":"codex","prompt":"Check build status","when":{"kind":"interval","minutes":60},"timeZone":"Europe/Istanbul","enabled":true}}
← {"type":"schedule.list.result","id":"s-2","schedules":[...]}
← {"type":"schedules.updated","schedules":[...]}

→ {"type":"schedule.run","id":"s-3","scheduleId":"sch-1"}
← {"type":"schedule.list.result","id":"s-3","schedules":[...]}
← {"type":"schedules.updated","schedules":[...]}
```

## Terminals and port forwarding

### In-folder terminal

A user shell running in a pseudo-terminal directly in the session's folder on the server (running `bash --noprofile --norc -i`).
Terminal output strips ANSI escape sequences and keeps a backlog of up to 200 000 characters for reconnecting clients.
Terminals are only available for sessions hosted on the local server, not on remote nodes.

- `terminal.open`: Opens or attaches to the session's shell. Returns `terminal.opened { id, terminalId, sessionId, backlog }`.
- `terminal.input`: Sends raw input text (`data` ≤ 64 000 chars, e.g. `"ls -la\n"` or `"\u0003"` for Ctrl-C) to the terminal stdin. Replies `ok`.
- `terminal.close`: Terminates the shell process with `SIGHUP`. Replies `ok`.
- Output is pushed to all clients as `terminal.output { terminalId, data }`.
- When the shell exits, `terminal.exited { terminalId }` is broadcast.

```json
→ {"type":"terminal.open","id":"t-1","sessionId":"sess-1"}
← {"type":"terminal.opened","id":"t-1","terminalId":"term-1","sessionId":"sess-1","backlog":"/srv/kervan/workspaces/sess-1 $ "}

→ {"type":"terminal.input","id":"t-2","terminalId":"term-1","data":"echo hello\n"}
← {"type":"ok","id":"t-2"}
← {"type":"terminal.output","terminalId":"term-1","data":"echo hello\r\nhello\r\n/srv/kervan/workspaces/sess-1 $ "}

→ {"type":"terminal.close","id":"t-3","terminalId":"term-1"}
← {"type":"ok","id":"t-3"}
← {"type":"terminal.exited","terminalId":"term-1"}
```

### Listening ports (`port.list`)

Inspects TCP ports listening on the server (excluding system ports < 1024 and Kervan's own server port) using `ss` (or `lsof`).
Returns `port.list.result { id, ports: [{ port, process? }] }`.

```json
→ {"type":"port.list","id":"pl-1"}
← {"type":"port.list.result","id":"pl-1","ports":[{"port":3000,"process":"node"},{"port":8080,"process":"python3"}]}
```

### Port preview tunnel (WebSocket)

Connects the client directly to a localhost TCP port on the server machine through a dedicated WebSocket upgrade.

- URL: `ws://<host>:7420/v1/tunnel?port=<N>`
- Auth: `Authorization: Bearer <token>` on the upgrade request.
- Query param: `port` must be an integer between 1 and 65535 (HTTP `400 Bad Port` if invalid).
- Behavior: Bi-directional stream proxy. Raw TCP bytes sent to `127.0.0.1:<port>` and received back are forwarded as binary WebSocket frames.
- If the target port cannot be reached, the WebSocket is closed with code `1011` ("port unreachable"). Normal disconnect closes with `1000`.

## Diagnostics and bug reports

Collects redacted server diagnostics for troubleshooting and bug reporting without disclosing secrets.

`Diagnostics`:
```typescript
{
  version: string;     // Kervan server version
  node: string;        // Node.js version
  os: string;          // e.g. "linux 6.8.0-49-generic x64"
  uptimeSec: number;
```

## Search

Whole messages are indexed (an agent's streamed chunks are joined). Every query word must match, as a word prefix.
Matching ignores case and Turkish/Latin diacritics, and treats `ı`, `İ`, `I` as `i`, so `rotasi` finds `rotası`.
`seq` is the first event of the matched message — the same id the client uses for that transcript row. In `snippet`
(≈120 chars of the original text) each match is wrapped in `\u0001` … `\u0002`.

```json
→ {"type":"session.search","id":"s-1","query":"deploy"}
← {"type":"session.search.result","id":"s-1","hits":[{"sessionId":"sess-1","seq":4,"role":"user","snippet":"Please \u0001deploy\u0002 the latest build"}]}
```

## Lead agents and helpers (M9)

A session created with `orchestrate: true` (or a team member whose role has `lead: true`) is a **lead**. Its agent
gets an extra stdio MCP server named `kervan` (`server/src/orchestra-mcp.ts`) with these tools:
`list_agents`, `start_helper {name, task, agent? | role?}`, `message_helper {helperId, text}`,
`wait_for_helper {helperId, timeoutSec?}` (default 50 s, max 600; returns `done: false` on timeout),
`list_helpers`, `stop_helper {helperId}`. At most 6 helpers per lead; helpers can't start helpers.

The bridge talks to the server over a Unix socket (`<dataDir>/orchestra.sock`, owner-only) with a per-start token
that names the lead, so a lead only reaches its own helpers. The MCP name `kervan` is reserved.

Helpers are ordinary sessions with `parentId` set to the lead; they work in the lead's folder (and join its team).
Messages the lead sends them are `user_message` events with `from: <lead session id>`. Their permission requests
reach the app like any other session's. A lead's own calls to these tools are approved by Kervan without a card
(matched by exact tool title; shell commands and edits always ask).

## Budgets, limits and helper worktrees (M11)

- `session.create` takes `budgetUsd` (0–10 000) with `orchestrate: true`; roles with `lead: true` may carry `budgetUsd`.
  `SessionInfo.usage {contextUsed, contextSize, costUsd?}` is what the agent last reported (ACP `usage_update`;
  cost only from agents that report one, cumulative across restarts). When a lead's and its helpers' cost reaches
  the budget, Kervan records a notice on the lead, cancels every running turn in the crew, and refuses
  `start_helper` / `message_helper`.
- Server limits: `KERVAN_MAX_HELPERS` (default 6 per lead), `KERVAN_HELPER_TURN_MINUTES` (default 30; 0 = off).
  A helper turn past the limit is cancelled with a notice.
- If the lead's folder is a git repository with a commit, `start_helper` (unless `isolate: false`) gives the helper
  its own worktree (`<workspaces>/worktree-<id>`) on branch `kervan/<name>-<id8>` (`SessionInfo.branch`).
  `helper_diff` shows the branch's changes (uncommitted work is committed first); `merge_helper` merges it into the
  lead's current branch with `--no-ff`, or aborts and lists the conflicting files. `merge_helper` is the one Kervan
  tool that is not auto-approved.

## Agent settings, terminal agents and resilience (M12)

- `SessionInfo.config: [{id, name, category?, value, choices: [{value, name, description?}]}]` holds the agent's
  select-style ACP session config options (model, thought_level, mode…), from `session/new`, `session/resume` and
  `config_option_update`. `session.config {id, sessionId, configId, value}` changes one (`session/set_config_option`);
  without a running agent the choice is stored, and it is re-applied whenever the agent restarts. Agents that offer
  models and modes the older way (Gemini CLI: `models` / `modes` on session/new and session/resume) get them as
  options `acp:model` and `acp:mode`, changed with `session/set_model` / `session/set_mode`.
- Agents with `protocol: pty` (agents.yaml or the app) run in a pseudo-terminal via `python3`'s `pty` module: each
  message is typed as one line, output (control sequences stripped, echo removed) streams back as
  `agent_message_chunk`, and a turn ends after `quietMs` (default 2000) of silence. No resume, preface or permission
  requests; they can't be leads. `agentDetails[].terminal` marks them.
- An agent process that exits on its own no longer ends the session: a notice is recorded and the next message
  starts it again (resumed, for ACP agents).
- The server copies its database to `<dataDir>/backups/kervan-YYYY-MM-DD.db` once a day (`VACUUM INTO`), keeping 7.

## Nodes (M13)

With `KERVAN_NODE_TOKEN` set, the hub accepts `kervan-node` processes on `/v1/node` (bearer = node token, header
`x-kervan-node: <name>`). Hub and node then make JSON calls both ways (`rpc.ts`): the hub calls `start`, `prompt`,
`cancel`, `close`, `setConfig`, `files.list|read|write` (base64, ≤ 50 MB); the node sends `event`, `usage`,
`config`, `exited` and calls `permission`. Workspaces on a node are keys (session or `team-<id>`) relative to its
own folder.

App-side messages:
- `node.list`: `id` → `node.list.result {id, nodes: NodeInfo[], hubAddresses: HubAddress[]}`
  `NodeInfo`: `{ name: string, connected: boolean, version?: string, lastSeen?: string, via?: string }`
  `HubAddress`: `{ address: string, kind: "tailscale" | "lan", network?: string, host?: string }` (`host`: the
  hub's MagicDNS name on Tailscale addresses, when the `tailscale` CLI reports one)
- `nodes.updated`: broadcast to all clients when nodes connect or disconnect (`{ nodes, hubAddresses }`).
- `node.invite`: `{id, name}` → `node.invited {id, name, code, expiresAt}` (single-use, 30 min expiration).
- `node.remove`: `{id, name}` → `node.list.result`, and broadcasts `nodes.updated`.
- Agents carry `node` in `agent.save` and `agentDetails[].node`. `agent.list.result.nodes` lists the assignable nodes.
- Work goes to a node by naming one of its agents: `session.create`, `schedule.save` and a lead's `start_helper` all take that agent's id, and `list_agents` reports each agent's `node` and `online`.
- Starting new work on a node that isn't connected fails with `node_offline` and creates nothing. `card.save`, and `schedule.save` with a project, refuse a node's agent because projects live on the hub; so do `session.create` with `orchestrate` or `split`.
- Messages to a session whose node is offline fail with `node_offline` and leave the session as it is; file routes answer 503.

### Node onboarding endpoints (HTTP)

These routes authorize using the single-use invite code instead of a bearer token:

| endpoint | purpose |
|---|---|
| `GET /v1/node/install?code=<code>` | Returns dynamic bash setup script (`text/x-shellscript`) configured with hub HTTP and WS URLs |
| `GET /v1/node/bundle.tar.gz?code=<code>` | Streams `server/` code archive without `node_modules`, `data`, or `test` |
| `POST /v1/node/join` | Body `{"code": "..."}` (≤ 4096 bytes). Trades the code for the node's credentials: `200 {"name": string, "token": string}` |

A node then connects to `ws://<hub>/v1/node` with its own name and token.
